# Morphology-balanced shared queue implementation plan

**Baseline** — Fetched `origin/main` at `b149547`. Implement this as an additive queue mode for new plans. Deliver incremental import and mirroring first, then balanced preparation and dispatch, so each can be tested independently.

**Goal** — Prepare the pool when an organiser clicks **Prepare queue** in Job Distribution and the selected dataset has no upload or indexing in progress. Use it to finish whole videos and keep usable frame counts as even as the imported supply and available annotation time allow across the morphology groups. Every new primary job has 30 frames except the single final remainder. A video or a deliberately selected clip counts toward the scientific collection once all its required frames have validated.

## How this fits the current app

| Current entry point | Change for the balanced queue |
| --- | --- |
| `datasets_api.finalize_dataset` and the successful mounted-folder index path in `mounted_datasets.py` | Mark the inventory ready and update its revision. Preparing the queue requires an organiser click. |
| `native_worker.worker_cycle` | Run local preparation on the mirror/bulk path, before requiring Supervisely credentials. Keep it out of status polling, validation and publishing. |
| `labeling_api.create_plan` and `approve_plan` | Expose **Prepare queue** and approve a specific prepared revision. Existing legacy and shared plans keep their current rules. |
| `native_operations_api.launch_event` | Keep the explicit launch action and the existing full-dataset mirror check. Preparation may run while Supervisely mirroring continues. Launch waits for mirroring. |
| `work_queue.claim_primary_block` | Route balanced plans to the new allocator after the existing event, plan, team, attendance and open-packet checks. Keep the existing job, packet and publish operation creation. |
| `native_worker.publish_job` | Keep the shared-primary path. A mixed-video job still publishes one list of 30 already mirrored image IDs. |
| `frame_submission.capture_frame_submission` and `validation_tasks.process_validation_once` | Reuse immutable accepted-frame records. Update progress for the actual video of each newly accepted frame, including when a job spans videos. |

The current shared mode builds fixed blocks at draft creation, after validating the roster. At runtime, it selects one saved block. The balanced mode prepares **ordered video runs** before anyone checks in. It packs the next job from those runs when the worker claims it. The allocator never scans the dataset directory or rebuilds the full pool during an assignment.

## 1. Prepare the pool on demand after either import path

### Append batches using browser ZIP or folder upload

The existing browser uploader creates a new dataset and finalizes one staging area. Separate uploads made through that entry point produce separate datasets. The shared plan points to one dataset, and the publisher expects all frame IDs in a job to belong to its one mirrored Supervisely dataset. Add **Add videos to this dataset** so both batches become revisions of the same collection. This workflow works without a mounted host folder.

- [ ] Reuse the resumable chunk protocol with a batch ID and separate staging directory under the selected dataset. Allow one open batch per dataset. Persist upload offsets and batch states (uploading, indexing, ready to commit, committed, failed, discarded). In a background task, checkpoint completed clips and their validated hashes in batch-owned storage. Recover an interrupted task from its last checkpoint. Resume or discard only the new batch. Publish inventory rows and the new revision in one database transaction after files are durably staged for use. On restart, distinguish files belonging to a committed batch from uncommitted files before cleanup.
- [ ] Accept one ZIP or one folder per batch in the existing species/video/frame layout. The ZIP root wrapper can be normalized by the existing importer. Upload complete extracted clip folders, using the same import policy each time. Permit the same species across batches. Reject a repeated species/video key, an overlapping canonical source range where known, and file replacement. Adding more frames to a previously imported video is outside this first version.
- [ ] Check archive safety, per-batch upload and expansion limits, cumulative dataset bytes and asset counts, and staging disk space. Validate and hash new files only. Publish the new inventory and bump its revision atomically, with recovery for staged files if interrupted. A rejected batch leaves earlier revisions usable.
- [ ] Requeue the mirror for the new revision and retain the same Supervisely project and image dataset. Resume from committed mappings and reconcile uncertain batches before retrying. A mirror run must record which revision it completed. If a batch commits during a previous mirror run, leave the new revision pending rather than letting the old worker mark it ready.
- [ ] Keep the same canonical inventory for ZIP and browser-folder inputs. A browser folder upload transfers files to the host just as a ZIP upload does. A mounted host folder is a separate input path and can use the same inventory and queue preparation once indexed. Supervisely receives the new images in the existing shared remote dataset, while Nightjar retains each image's species, video and ordinal.
- [ ] Block append on a launched pool. Before launch, require revoking approval of an already approved pool before accepting a batch. While a batch is open, uploading, or indexing, disable **Prepare queue** and enforce the gate server-side. Once the final batch is indexed, the organiser clicks **Prepare queue**, reviews combined coverage and approves the current revision. Launch waits for its mirror.
- [ ] Rehearse a ZIP followed by a browser-folder batch and the reverse, using complete clips from overlapping species folders. Interrupt indexing after a clip checkpoint and mirroring after Supervisely accepts an image batch but before its mappings commit. Verify restart resumes without duplicates, failure or discard preserves the first batch, and the combined queue can issue one 30-frame job spanning the two batches. Verify that an older mirror run finishing after an append cannot enable launch.

### Pause and resume the Supervisely upload

- [ ] In the Dataset tab, put **Pause Supervisely upload** and **Resume Supervisely upload** beside the mirrored frame count. Show **Pausing** while a batch is in flight, then **Paused — safe to shut down Nightjar** once the worker has stopped and persisted progress. These controls apply to the transfer from Nightjar to Supervisely.
- [ ] In `datasets_api.py` and `native_media_pool.py`, persist the organiser's pause request per dataset. An idle or queued mirror can pause immediately. Before starting each remote upload batch, check the saved pause request. Let any in-flight batch finish and save its image IDs before acknowledging the pause. Serialize batch admission with pause requests so an acknowledged pause cannot admit another upload. Persist the pause across worker and PC restarts, including when an append creates a newer inventory revision.
- [ ] Resume with a single worker claim against the same Supervisely project and dataset. Reuse committed image mappings and reconcile by stable image identity before retrying any batch with an uncertain outcome. If the PC shuts down while **Pausing**, recover the interrupted claim and reconcile that batch on resume. A pause leaves local indexing and queue preparation available once their own readiness checks pass. Launch still requires a complete mirror for the approved revision.
- [ ] Test pause with a queued and an in-flight batch, then restart while paused and verify zero new uploads until Resume. Test a shutdown after Supervisely accepts a batch but before Nightjar saves its mappings. Verify the resumed upload creates no duplicates, including when a new ZIP or folder batch was indexed during the pause.

### Full dataset layout and morphology mapping

Use the demo as a layout reference: `dataset-root/species-folder/video-folder/species_f000000.jpg`. Identify each video or selected clip by its species folder and video folder together. Resolve frame order from the numeric suffix within that clip and allow ordinals to start above zero. A contiguous range describes the supplied clip. Use an explicit manifest when the expected source boundaries need to be verified.

Use the workbook's **Source Folder Inventory** to map species folder keys to the groups in **Morphology Rules**, and its **Species Catalogue** to resolve additional species. Reuse the workbook-derived reference already in Nightjar. Apply organiser overrides first and normalize folder keys with the existing resolver. The worker uses the resolved mapping saved with the approved draft. Flag unknown species in the preview for classification.

Exclude `_sampled` variants from the balanced primary pool and validate density and ordinal continuity independently. Use the species folder as the classification key even if the filename prefix differs. Calculate supply and the preview from the actual full dataset at import.

Preserve parsed source ordinals, including zero-based filenames, and distinguish them from ordinals inferred by sorting. For balanced eligibility, require unique consecutive source ordinals from filenames, an explicit manifest, or original-video extraction. A gap-free supplied range establishes continuity within that clip. Use a manifest or original-video metadata to verify completeness against declared boundaries. Keep inferred-order imports usable in existing modes and show why they were excluded from balanced preparation.

- [ ] Test the layout with both browser and mounted-folder imports. Cover multiple videos per species, a clip starting above zero, sampled variants, an unsuffixed folder with missing frames, and an unknown species that becomes eligible after the organiser classifies it.

- [ ] Enable **Prepare queue** only when the selected dataset has a finalized local inventory and no pending or running browser upload, append scan, or indexing task. Show the reason when disabled. Enforce the same check on the API under the dataset lock so another browser or a stale tab cannot bypass it. Queue preparation uses no roster or attendance checks. Treat remote mirroring as a separate status and keep the existing mirror requirement at launch.
- [ ] Add a durable preparation request keyed by dataset and configuration revision. Reuse an existing operation type mechanism where practical. Make it possible to retry preparation independently of mirroring. Workers claim requests atomically. A process crash must leave a request recoverable and never publish half a draft.
- [ ] Build the draft from the imported inventory, using the current full-density and gap-free ordinal rules. Read frame identity and folder metadata from PostgreSQL. The import has already indexed and hashed the files. Store each run as a video ID, first ordinal and frame count, using the existing unique `(video_id, frame_index)` index to resolve frames. For the first version, treat each eligible imported video folder as one complete source unit.
- [ ] Use the same morphology resolver as Dataset Coverage. A confirmed organiser override wins over the reference suggestion. Freeze the group and source provenance on approval. Flag unclassified videos and known overlapping sources. When provenance cannot establish whether two clips overlap, report that uncertainty. Identical image bytes alone are insufficient to identify a duplicate temporal frame.
- [ ] Include all eligible whole videos from the approved import. Show eligible frames, videos and species by morphology. Groups with no eligible footage remain visible with zero supply. There is no fixed frame target, per-group cap, or automatic exclusion of surplus footage. Within a group, use deterministic species rotation when choosing the next video where practical.
- [ ] Separate preparation state from approval and mirroring. Use a revision check when committing prepared data so a stale worker result cannot overwrite a newer draft. A changed classification or dataset inventory marks the draft stale. Require a fresh click once local work finishes. Serialize starting preparation and local inventory changes under the dataset lock, and recheck the revision and readiness before publishing or approving the draft. Reuse the same draft instead of creating duplicates. Support datasets imported before this release.
- [ ] Keep prepared drafts advisory until approved. Before approval, check that the revision is current, there are eligible videos, the organiser can see missing groups and exclusions, and existing jobs/plans do not conflict. After approval, extend manual-assignment and other plan guards to cover the selected video runs. Those guards currently use existing jobs and WorkBlock rows. Add coverage for both UI reservation indicators and API rejection. Keep the approved inventory fixed.

## 2. Pack 30-frame jobs under the existing claim lock

- [ ] Add an explicit balanced mode to the plan and a per-plan video record with planned size, next unassigned ordinal, accepted count, classification and selection order. Index the ready tails and unopened candidates. Preserve the plan-only allocation lock and one-open-packet constraint. Check event eligibility without acquiring an event row lock from the claim path. Keep the existing lock order.
- [ ] Fill a candidate job from started videos first, preferring those with the fewest frames left to validate. Skip videos whose remaining frames are already assigned or awaiting correction. When opening a new video, choose the morphology with the fewest projected frames among groups that still have an unopened eligible video. Projected frames are completed-video frames plus the full length of started unfinished videos. Compare absolute counts to keep representation even during the event, and use a stable tie-break. Once a group exhausts its supply, continue with the other groups. Balance determines dispatch order. If every imported video finishes, the final totals reflect the supply in the import.
- [ ] Example: use the last 16 unassigned frames from Video A, followed by the first 14 from Video B. Keep the source-video identity and ordinal of each frame. B now counts as started. Each video completes independently.
- [ ] Treat the unfinished-video limit as a soft target. Use assignable tails from started videos first. If those tails cannot fill a job and opening videos is still allowed, exceed the target and open the minimum number of videos needed by the existing selection order to fill the job. Do this in the same claim, without waiting for someone else to submit, a correction to finish or a timer to fire. Record when a claim exceeds the target. Persist the cursor changes, job, work packet and publish operation together. A failed claim rolls all of them back. Keep all remote calls outside the claim transaction.
- [ ] Before the scheduled end, stop opening videos using a configurable finish window. For the first release, choose the window from rehearsal rather than adding an untested throughput predictor. Continue dispatching full jobs from open-video tails. Under the same claim lock, seal the intake of new videos and issue a single short remainder only when the eligible unassigned pool is permanently below 30. The selected pool running out is also a terminal condition. A pause, a temporary concurrency limit or a single video tail never qualifies. Corrections retain the existing missing-frames-only behavior.
- [ ] Keep the claim query bounded by video metadata and the selected ranges. Resolve at most 30 IDs using indexed ordinals, and verify that every ordinal exists before committing. Measure claim lock wait and duration separately from Supervisely publish time. Mixed-video packing creates no extra remote jobs or frame uploads.

## 3. Record accepted frames and report completed videos

- [ ] Update progress from the newly accepted `ReviewSample` rows in the same transaction as acceptance. Serialize with allocation and check the validation lease before committing. Handle retries and corrections without counting an already accepted source frame twice. Review scores, repeat jobs and manual jobs remain independent of morphology allocation.
- [ ] Preserve the current validation transaction boundary. Commit accepted frames and their progress with the validator's task completion before attempting successor allocation. Ensure retries after allocator contention do not recount accepted frames. Exercise inline capture and separate validation workers, including a lost lease before acceptance commits.
- [ ] Show planned, in progress, validated and usable frames by morphology in Job Distribution, with a separate list of started or stalled videos and their missing counts. For a 300-frame video with 299 validated frames, report 299 validated and zero usable. Keep its accepted snapshots available.
- [ ] Export a complete-video manifest from accepted immutable snapshots with group, species/folder, source video and ordinal, source identity/hash, snapshot reference and review status. List incomplete videos and missing frames separately. Use a bounded/streamed read. The raw Supervisely export is a separate dataset source.
- [ ] Integrate with main's existing draining closeout. Include frames accepted during the drain in the frozen collection manifest, and verify that submissions after the cutoff cannot change it. Add migrations after the current head and test the upgrade with existing data.

## 4. Test and roll out

- [ ] Test manual preparation after browser and mounted-folder imports with an empty roster. Verify that import alone never prepares a draft, preparation is rejected during uploads and indexing, and appending footage makes the old draft stale until the organiser prepares again. Verify the launch gate separately while mirroring is in progress. Cover retries after a preparation crash, concurrent claims of the preparation task, stale drafts, classification overrides, zero supply and uneven morphology supply and continued allocation after a smaller group runs out.
- [ ] In PostgreSQL test 16+14 across videos and morphologies, multiple short tails, deadline sealing, one final short job under concurrent claims, and rollback before publishing. At the unfinished-video target, hold every started video's remaining assigned frames in unresolved jobs or corrections. Verify concurrent claimers still receive full jobs from eligible unopened videos without any of those held jobs finishing. Also test a 16-frame tail at the target and verify that the next claim immediately opens another video for the remaining 14. After deadline sealing, verify that the override cannot open a new video. Verify disjoint frame IDs, original frame order within runs and the existing one-active-job rule. With uneven supplies, check that opening new videos favours the least-covered available groups and that finishing all work retains the original eligible supply totals.
- [ ] Test partial submission, correction and validator restart. Verify that mixed-video progress goes to each source video, repeated validation does not inflate progress and only complete videos enter the manifest. Test competing manual assignment, old plan approval, late check-in, pause/resume and archive.
- [ ] Rehearse preparation on 100,000 indexed frames and compare 200 simultaneous assignment requests against the existing shared queue with the same simulated remote latency. Record preparation time, claim p95 and maximum, event lock waits, first and last published jobs, usable frames by morphology, and unfinished videos at an early cutoff. Use the results to choose the unfinished-video limit and finish window. Keep preparation out of launch timing.
- [ ] Run the full backend suite, PostgreSQL concurrency suite, frontend build and migration against a populated disposable database. Verify existing legacy/shared plans keep their original behavior. Enable the balanced mode on a new plan after the rehearsal.
